# 设计目标与设计步骤

> 本文件只记**要做什么、按什么顺序做、怎么算做完**。架构细节在 `ARCHITECTURE.md`，数据格式在 `DATA-MODEL.md`。
> 内容来源：用户原话拆解（2026-11-11，第二次细化）。

---

## 1. 项目定位

**VGM 结构化编辑器 / 跨芯片移植工具。**

不是 tracker，不是 VGM 转换器。是：

> **真正的导入 / 结构化 → 按音符为单位改写 → 输出到芯片写入引擎 → 生成合规 VGM。**

与"转换器"的区别：转换器是把 A 格式的数据机械翻译成 B 格式。我们做的是**先真正理解**（把寄存器日志结构化成按音符分块的事件），**再真正重写**（用芯片的驱动层产出正确的写序列）。中间那层"理解"是无损的、可回溯的、可编辑的。

---

## 2. 完整数据流

```
                        ┌─────────────────────────────────────────┐
  input.vgm  ──────────►│ ① 导入：libvgm 解析 → 寄存器流 → 按音符分块 │
                        └─────────────────────────────────────────┘
                                            │
                                            ▼
                        ┌─────────────────────────────────────────┐
                        │ ② source.json（源芯片）                  │
                        │    chips / regStream / notes / global    │
                        │    时间单位 = 采样数；无 BPM              │
                        └─────────────────────────────────────────┘
                                            │
                        ┌─────────────────────────────────────────┐
                        │ ③ 编辑器前端                             │
                        │    · 按音符编辑（时间/音长/音高/力度）    │
                        │    · 音色编辑（抄 furnace 的 insEdit）    │
                        │    · 通道映射设置（8ch → 9ch）            │
                        │    · 跨芯片音色映射（OPM → OPLL）         │
                        └─────────────────────────────────────────┘
                                            │
                                            ▼
                        ┌─────────────────────────────────────────┐
                        │ ④ target.json（目标芯片）                 │
                        │    同一 schema，不同 chip 描述            │
                        └─────────────────────────────────────────┘
                                            │
                        ┌─────────────────────────────────────────┐
                        │ ⑤ 输出：furnace dispatch 层              │
                        │    按音符驱动芯片 → 记录寄存器写 → VGM 字节 │
                        └─────────────────────────────────────────┘
                                            │
                                            ▼
                                      output.vgm
```

**关键：JSON 是唯一的中间态，且具备两个能力**

| 能力 | 含义 |
|---|---|
| **JSON ↔ VGM** | 从 JSON 能重建出可播放、合规的 VGM；从 VGM 能还原出等价的 JSON（L0 层位精确） |
| **实时播放** | 编辑器里点播放，声音直接来自 JSON，不用先落盘成 VGM |

## 3. "结构化"的定义（必须记住）

用户原话：

> 不对 VGM 做任何量化，也不做 VGM 转 MIDI。
> 只是忠实地按通道记录 VGM 里的寄存器信息。
> json 虽然所有东西都按原值显示，但是它按照事件会进行划分，比如按照音符进行划分。
> json 实际上是按采样数为时间单位，以通道、全局寄存器为分类标准，按音符事件划分为块。

拆成五条可执行规则：

| # | 规则 |
|---|---|
| S1 | **时间单位 = 采样数**。整个软件的时间轴都是采样数，不是 tracker 行、不是网格、不是 tick。 |
| S2 | **不记录 BPM**。VGM 是日志格式，里面没有 BPM。BPM / 网格只是 UI 上的**参考值**，可显示可关闭，不影响数据。 |
| S3 | **分类标准 = 通道寄存器 + 全局寄存器**。每个通道一组（YM2151 8 个通道），全局一组（LFO、noise、timer 等）。 |
| S4 | **按音符事件划分块**。寄存器流不是一条扁平的长链，而是切成一个个"音符块"：一个块 = 一次 key-on 到 key-off 之间的全部寄存器写。 |
| S5 | **原值显示**。块里存的是 `(reg, val, atSample)` 原值，不是换算后的音高/音量。音高/音名是视图层的推测。 |

### S4 的划分依据（参考 modizer 的合并规则）

modizer 把 VGM 画成钢琴条时用的合并判据（`RenderUtils.mm:5965-6015`，约 50 行）：

| 条件 | 动作 |
|---|---|
| 音高改变 | 断开，新块 |
| 通道改变 | 断开，新块 |
| 音量上升（重触发） | 断开，新块 |
| `VOICE_ON` 清零 / 音高为 0 | 断开，块结束 |
| 音量下降（连奏衰减） | **不断开**，继续延长同一块 |

这套判据经过实战验证，我们直接采用。但**时间单位必须从它的"1/60 秒帧行"换成采样数**——modizer 是为渲染服务的，我们是数据层。

## 4. 第一阶段的三件事（G1–G3）

| # | 目标 | 精确定义 | 不包含 |
|---|---|---|---|
| **G1** | **正确显示** | 从 source.json 推出音符块，画成横向音条；位置、数量、先后顺序正确 | 不求音高/音名正确，不求美观 |
| **G2** | **正确播放** | 从 source.json 重建寄存器流，喂 libvgm，出声且与原文件一致 | 不做编辑、不做输出 |
| **G3** | **正确进度** | 播放头 = 播放器真实采样位置；时间轴总长 = 总采样数 | 不用墙钟估算 |

**第一阶段不追求"可视化准确"，只追求"显示得出来、播得对、进度对"。**

## 6. 跨芯片的等价性分析（YM2151 → YM2413）

用户原话：

> 原芯片 8 个通道，目标芯片 9 个通道，时域信息肯定是相通的，如音符时间，音长，音高也基本上可以对等映射，只有音色是有区别的。

| 维度 | YM2151（OPM） | YM2413（OPLL） | 映射关系 |
|---|---|---|---|
| 通道数 | 8（全部 FM） | 9（全部 FM，2-op） | 8 → 9，**多出的 1 个通道空置**，不是问题 |
| 时间 | 采样数 | 采样数 | **完全相同**，直接搬 |
| 音符起始 | key-on 时刻（采样） | key-on 时刻（采样） | **完全相同** |
| 音长 | key-off − key-on | 同 | **完全相同** |
| 音高 | KC(8bit) + KF(6bit) → F-Number | F-Number + Block（`0x10+ch` / `0x20+ch`） | **可对等**：都走 F-Number 公式，只是精度不同 |
| 音量 | 载波 TL（7bit，按 ALG 选载波） | `0x30+ch` 高 4 位（0-15） | 需**降精度**：7bit → 4bit |
| **音色** | **4 operator 自由参数 + 8 种 ALG** | **2 operator + 15 个 ROM 预置 + 1 个用户音色** | **唯一的真正难点** |

### 音色差异的具体量化（已核实）

| 参数 | OPM 位宽 | OPLL 位宽 | 处理 |
|---|---|---|---|
| `ar` 起音率 | 5 bit（0-31） | 4 bit（0-15） | 右移 1 |
| `dr` 衰减率 | 5 bit（0-31） | 4 bit（0-15） | 右移 1 |
| `rr` 释放率 | 4 bit（0-15） | 4 bit（0-15） | 直接搬 |
| `sl` 延音电平 | 4 bit（0-15） | 4 bit（0-15） | 直接搬 |
| `tl` 总电平 | 7 bit（0-127） | mod 6bit / car 4bit | 需重标定 |
| `ksr` 键缩放率 | 双义（KSR / TL-ramp） | 1 bit | 取最高位 |
| `mul` 频率倍数 | 4 bit（0-15） | 4 bit（0-15） | 直接搬 |
| `dt1` 失谐 | 3 bit | 3 bit | 直接搬 |
| `dt2` | 2 bit | **无** | 丢弃 |
| `d2r` | 2 bit | **无** | 丢弃 |
| `alg` 算法 | 3 bit（0-7） | **1 bit（SUS）** | 按载波数折算 |
| `fb` 反馈 | 3 bit | 3 bit | 直接搬 |
| operator 数 | **4** | **2** | 只取 op1(op2 调制) + op2(载波)，op3/op4 丢弃 |

### 两条可行路径

**路径 A：匹配 15 个 ROM 预置（推荐先做）**

用 Nearest-Neighbor 在 OPLL 的 15 个 ROM patch 里找与 OPM 音色最接近的一个，只设 `opllPreset` + 载波 `tl`（音量）。

- 优点：**音色一定正确**（用的是真实 ROM 数据），实现简单，出声不会有怪味
- 缺点：音色是"最接近的预置"，不是原音色的降级
- Furnace 内部就是这条路：`opllPreset != 0` 时丢弃 op 参数，只保留 `op[1].tl` 作音量（`insTabFM.cpp:1692`）

**路径 B：用户音色（preset 0）**

把 OPM 的 op1/op2 参数按上表映射，打包进 OPLL 的 8 条用户音色寄存器。

- 优点：保留更多原音色特征
- 缺点：**全芯片只有一个用户音色槽**，9 个通道共用，多音色曲目就崩了
- 除非整曲只有一个音色，否则不可行

**结论：主路径走 A（预置匹配），B 作为"单音色曲目"的可选增强。**

## 9. 三个外部依赖的分工（一句话）

| 依赖 | 职责 | 不负责 |
|---|---|---|
| **libvgm** | VGM 解析、芯片仿真、音频渲染 | 不负责结构化、不负责写 VGM |
| **furnace dispatch** | 芯片正确写序列、寄存器记录、VGM 字节生成 | 不负责导入、不负责 UI |
| **0x808** | 窗口、ImGui、走带、布局 | 不负责任何芯片逻辑 |
